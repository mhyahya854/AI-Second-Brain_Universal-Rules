## RC4-specific attack topics — NOT AN ISSUE

Each item is a rejected defect hypothesis, not a finding. No repair is indicated; changing these boundaries without evidence could weaken explicit owner policy or create a new universal algorithm.

1. **NAI-01 — Literal complete JSON reconstruction (HIGH confidence).** Rule/quote: JSON-1 requires “the actual recoverable contents of the entire retained logical workspace.” Scenario: recovery relies on hashes or a pointer to a missing object store. JSON-1/2/3 explicitly require payload coverage, exact byte reconstruction and inventory of workspace-level components; hash/pointer-only recovery is disallowed. Smallest fix: none. Regression risk from a change: silent loss of the requested dual-payload contract.
2. **NAI-02 — Recursive self-inclusion (HIGH).** Rule/quote: JSON-3 requires “a mathematically finite serialization and reconstruction policy.” Scenario: master-data.json includes itself or unbounded snapshots of itself. JSON-3.1–3.3 explicitly excludes recursive/generated envelopes and requires defined reconstruction and hash domains while preserving non-derivable retained content. Smallest fix: none; the App Plan must choose the concrete finite boundary. Regression risk: either infinite recursion or accidental omission of retained content.
3. **NAI-03 — Unbounded global serialization cost (HIGH).** Rule/quote: JSON-1 mandates complete payloads; WORKSPACE-TEST-2 says “If literal duplication cannot meet the agreed workload, present the material conflict honestly to the owner.” Scenario: a media-heavy workspace exceeds phone disk, memory, transfer or latency limits. The policy acknowledges the roughly 11/3 binary-volume lower-bound illustration, nested-envelope overhead, peak buffers and workload evidence; it leaves implementation optimization and supported envelope to planning and forbids silently replacing payloads. This is an intentional requirement with an explicit conflict path, not a false claim that it is cheap or universally feasible. Smallest fix: none within this review. Regression risk: removing it would undermine the owner-selected recovery contract.
4. **NAI-04 — Simultaneous writers (HIGH).** Rule/quote: JSON-4 says “Saving/acknowledgement timing, staging format, write protocol and universal authoritative-copy topology remain unresolved.” Scenario: two devices or an offline client update the same large global JSON. The candidate requires current-state coordination, explicit conflict/reconciliation and an App Plan decision before production implementation; it does not treat timestamps, matching hashes or hub status as authority. Smallest fix: none; no universal algorithm should be invented here. Regression risk: prematurely endorsing a topology without workload/platform evidence.
5. **NAI-05 — Syntactically valid but semantically wrong JSON (HIGH).** Rule/quote: JSON-4 states “A newer timestamp, matching hash, syntactically valid JSON or equal copies alone does not establish legitimacy, factual correctness or successful commit.” Scenario: a valid AI-generated transcript or incorrect edit is copied into both current layers. Evidence/provenance dimensions, operation receipts, common-state review and protected history prevent format validity or duplication from being treated as truth; no system can infer every domain fact from JSON validity. Smallest fix: none. Regression risk: a “valid JSON means safe” rule would fabricate correctness.
6. **NAI-06 — AI mistake propagated to both layers (HIGH).** Rule/quote: REV-2 protects recovery “in addition to the two current JSON layers.” Scenario: an authorized but incorrect bulk edit propagates before a user notices. Independent protected historical points, restricted ordinary deletion authority, validated adoption and content/provenance distinctions address recovery; they do not claim to prevent all authorized mistakes. Smallest fix: none. Regression risk: requiring every consequential AI operation to be interactive would contradict explicit bounded delegation without adding assurance against human mistakes.
7. **NAI-07 — Protected history erased or resurrected (HIGH).** Rule/quote: REV-2 says “Authorized erasure/expiry remains enforceable under PRIV-1.” Scenario: restore reintroduces a payload already legitimately erased, or routine credentials delete every history generation.
