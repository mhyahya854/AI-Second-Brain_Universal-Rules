## A — Normative logic

1. **Preservation used to defeat emergency containment or erasure — NOT AN ISSUE; high confidence.** Attack: an archive invokes LIFE-2, permanent provenance, and backup preservation to block credential revocation, retain erased payloads, or restore legally deleted information. SAFE-2 says: “A global ranking MUST NOT force data preservation when it creates greater human, physical, security, or privacy harm or defeats applicable erasure duties.” PRIV-1 says: “Restore MUST account for applicable deletion decisions rather than silently reinstating information contrary to policy.” GOV-3 says: “An exception MUST NOT present an unmet engineering guarantee as satisfied.” Retention, evidence, and recovery are explicitly bounded by authority and obligations. Smallest repair: none. Overcorrection risk: an absolute deletion rule could destroy legitimately protected evidence or recovery copies.

2. **Owner exceptions launder impossible guarantees — NOT AN ISSUE; high confidence.** Attack: approve a “NAS-safe” exception for an unsupported storage configuration, then call it conformant durability. GOV-3 requires revised scope, claims, residual risk and actual authority, and says: “Approval cannot waive physical constraints or applicable legal obligations by declaration.” TEST-1 separately requires supporting evidence. Policy approval cannot become technical verification. Smallest repair: none. Regression risk: removing exceptional-conflict handling would create unsafe immediate-change obligations.

3. **RF-01 research exception permits production implementation before freeze — NOT AN ISSUE; high confidence.** Attack: label a full product build “research,” perform destructive experiments on retained originals, and later treat existing code as established architecture. DEV-5 requires a bounded research question, evidence scope and limitations, and states: “the label does not authorize destruction of retained source data or required evidence”; “Incorporation of experimental code or behavior into the product MUST pass the normal Plan Freeze, phase, conformance, security, testing, and evidence requirements”; “‘Prototype’ or ‘research’ MUST NOT become a loophole for implementing substantial production scope before planning.” DEV-2, DEV-11 and DEV-13 remain operative. Smallest repair: none. Regression risk: undoing the clarification would again obstruct necessary feasibility evidence.

4. **RF-02 forces a materially failing report to claim a clean outcome — NOT AN ISSUE; high confidence.** GOV-5 says: “A report identifying any BLOCKER or MATERIAL finding MUST NOT assert the clean-result sentence as its outcome”. The operational protocol agrees. Smallest repair: none. Regression risk: simplifying away that conditional would restore the original ambiguity.

## B — Proportionality

5. **Tiny formatter inherits archive/scanner/NAS bureaucracy — NOT AN ISSUE; high confidence.** Attack: require an ephemeral stdin/stdout formatter to build backup, Raw intake, daemon, model, and 33 separate skill packages. GOV-1 says: “A stateless formatter does not need a backup engine; an application without AI does not need AI tool tests.” IO-1 exempts harmless bounded values from scanning without benefit. IO-2 permits no Raw/scanner infrastructure when relevant intake is absent. SKILL-4 governs the ecosystem library blueprint and permits combined workflow implementations; it does not require every application to install every family. DEV planning/state/gates still intentionally apply proportionately; concise combined records are expressly permitted by GOV-2 and DEV-6. Smallest repair: none. Regression risk: blanket tiny-app exemptions could omit materially dangerous behavior in small utilities.

6. **Lifelong archive evades safeguards by invoking proportionality — NOT AN ISSUE; moderate-high confidence.** DEV-16 requires an expected lifetime envelope and validation of relevant restore, migration, export, rebuilding and integrity operations. BACKUP-2 says important-data recoverability “MUST be validated at a proportionate cadence defined in the App Plan.” DEV-7 requires relevant compromise and backup protection planning for substantial retained-data apps. An implementation can choose bounded claims and accept disclosed risks; it cannot call absent evidence a passed guarantee. Smallest repair: none. Regression risk: universal numerical thresholds or mandatory infrastructure would recreate proportionality defects.

## C — 20–50-year lifecycle

7. **Dead provider/compiler and lost developer make retained information unrecoverable — NOT AN ISSUE; high confidence.** LIFE-2 requires “a practicable preservation and exit path beyond a particular runtime or vendor’s lifetime”. SEC-5 requires material disappearance-risk dispositions and honest reconstruction limits. BACKUP-1 covers the complete recovery dependency set; DATA-2 states: “If exact artifact identity matters, preserve the artifact for its required lifecycle rather than relying on unproven regeneration.” RECOVER-1 prohibits normal startup being the only recovery route for otherwise recoverable important state. No perpetual rebuild promise is made. Smallest repair: none. Regression risk: requiring all historical toolchains forever would conflict with security, licensing and purpose-limited retention.

8. **Ancient client silently erases new fields during recovery or sync — NOT AN ISSUE; high confidence.** MIGRATE-2 says: “An older application MUST NOT silently write or downgrade a newer data/workspace format it does not understand.” It also forbids claiming faithful read/export behavior without a supportable contract. SYNC-1 and MIGRATE-1 preserve authority, version and concurrent-work obligations. Smallest repair: none. Regression risk: requiring every old/new pair to interoperate would create impossible compatibility promises.

## D — Data loss/ransomware/synchronization

9. **One compromised client encrypts replicas, destroys NAS history and selects an infected immutable backup — NOT AN ISSUE; moderate-high confidence.** SYNC-1 requires a risk-based bulk-change policy and a containment route; SEC-1 requires assessing and limiting unnecessary propagation to replicas, histories, backups and secrets. BACKUP-1 requires considering recovery outside the same ordinary credential/failure boundary and documenting chosen protection and residual risk. BACKUP-2 says: “Older or immutable does not automatically mean clean”. Independent recoverability is not promised for every possible root compromise. Smallest repair: none. Regression risk: mandating immutable retention universally could defeat authorized erasure or unsuitable deployment constraints.

10. **Stale replica resurrects erased data; recovery rolls back newer legitimate work — NOT AN ISSUE; high confidence.** SYNC-1 requires explicit semantics for “Tombstone retention, long-offline replicas, and reintroduction of erased information”. PRIV-1 governs restored deletion decisions. RECOVER-1 says: “Restoring old global state MUST NOT be presented as safe undo without accounting for newer valid work.” MIGRATE-1 forbids unconditional snapshot restoration after failure. Exact tombstone horizon, reconciliation protocol and restore procedure belong in the App Plan. Smallest repair: none. Regression risk: universal permanent tombstones could unnecessarily preserve sensitive metadata.

## E — Malware/Raw/ClamAV

11. **Skipped, truncated or encrypted scan becomes CLEAN — NOT AN ISSUE; high confidence as policy, important adapter test.** Concrete trap: an adapter maps successful ClamAV process completion to CLEAN even when resource limits excluded relevant content. Official ClamAV documentation describes oversized files being skipped under `--max-filesize`. IO-3 says: “Failure to scan MUST NOT equal clean.” IO-2 requires the configured intake gate to succeed and forbids pending, failed, stale or unavailable verification silently satisfying it. IO-3 defines CLEAN only relative to recorded scanner/signature/policy state; TEST-1 requires integration evidence. The constitution does not provide the adapter’s exact completeness-detection mechanism. That is an implementation obligation, not permission to misreport results. Smallest repair: none. Regression risk: demanding exhaustive decoding of every container would be infeasible and could worsen resource-exhaustion risk.

12. **Scan/promotion TOCTOU, infected Raw synchronization and remote verdict laundering — NOT AN ISSUE; high confidence.** IO-2 says: “Bind promotion to the actual verified content/version and current applicable policy; intervening changes invalidate unsupported verdict reuse under [CON-1].” IO-3 requires receiving-device trust policy and says a remote CLEAN verdict must not become permanent universal trust. Synchronizing untrusted bytes does not authorize ordinary processing. Smallest repair: none. Regression risk: mandatory full rescan on every launch/update would damage large-library operation without proving safety.

13. **False positive destroys the only original; compromised scanner receives archive/backup authority — NOT AN ISSUE; high confidence.** IO-2 says: “A scanner detection alone MUST NOT automatically destroy retained source content.” Quarantine must provide effective isolation; a folder name is insufficient. SEC-1 requires role-appropriate authority and limits unnecessary compromise propagation. SEC-6 preserves core-controlled mutation and says scanner failure gives it no canonical mutation authority. These outcomes still require implementation-specific isolation and recovery evidence. Smallest repair: none. Regression risk: absolute source retention would obstruct legitimate erasure and emergency containment.

14. **ClamAV preference forces unsafe TCP, Linux-only features or incompatible redistribution — NOT AN ISSUE; high confidence.** SEC-6 permits replacement, prohibits exposing unauthenticated scanner TCP to untrusted networks, forbids Linux-only on-access functionality becoming universal, and requires actual licensing verification before distribution. LANG-1 separates dependencies from authored implementation components. Primary-source checks support these scoped cautions; no universal linking/process licensing exemption is claimed. Smallest repair: none. Regression risk: treating process separation as automatic license compliance would introduce a false guarantee.

## F — Agent Skill supply chain

15. **Reviewed root skill downloads mutable instructions, traverses symlinks and exfiltrates through host shell — NOT AN ISSUE; high confidence.** SKILL-3 requires review of supporting resources, installers, scripts/dependencies, symlinks/path traversal, dynamic resources, credentials and permissions. It says: “Dynamically fetched remote instructions MUST remain untrusted until validated.” SKILL-2 says a skill must not “inherit every capability available to its host AI.” AI-2 requires enforceable restrictions rather than prompt obedience; PRIV-2 separately constrains disclosure. A reviewed root file alone cannot authorize an unreviewed remote child or broad shell invocation. Smallest repair: none. Regression risk: forbidding all dynamic resources would unnecessarily preclude legitimate versioned workflows.

16. **Skill conflicts/context overload erase governing policy; trusted registry becomes immunity claim — NOT AN ISSUE; high confidence.** SKILL-1 requires overlap priority/conflict handling and supports progressive loading. SKILL-2 preserves governing contracts and project-specific phase requirements. SKILL-3 says: “Presence in a registry is a recorded trust disposition, not proof of immunity.” Insecure/obsolete skills must have trusted invocation reconsidered. Concrete context-window enforcement and skill validation remain implementation concerns. Smallest repair: none. Regression risk: imposing one fixed skill count or complete simultaneous loading would worsen small-model usability.
