# Universal Rules

This repository defines a governance constitution for software in this ecosystem. The primary normative document is [Universal Rules for All Apps](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md). Its original filename is retained for continuity.

The rules are a blueprint and development system intended to keep applications maintainable, understandable, recoverable, portable, evolvable, AI-continuable, user-controlled, coherent, and useful over many years. App designs remain specific to their users, domain, risk, data, platforms, and lifecycle.

## How to read the constitution

Universal invariants describe defensible engineering outcomes such as truthful operation results and enforced authority. Ecosystem policies are deliberate choices: they need not be laws of computer science. Defaults, conditional requirements, recommendations, and prohibitions have distinct strengths and applicability. Every candidate rule has a stable ID, provenance, and applicability; all inherit CANDIDATE status.

The principal ecosystem choices are:

- **Rust-first:** Rust is presumptive for new software. Non-Rust components need a concrete technical justification and scoped policy approval. Rust is not proof of correctness. See [LANG-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#lang-1) and [ADR-0001](decisions/ADR-0001-rust-first.md).
- **Feature-first:** Applications with multiple meaningful capabilities organize around deliberate responsibility and state ownership. No universal folder ceremony is required. A modular monolith is the ordinary default, with justified process/service boundaries permitted. See [architecture](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s06).
- **NAS support:** Applicable applications support declared, tested modes needed for their workflow. Hosting, service clients, ordinary shared files, raw transactional database access, and backup destinations are different modes. Docker or backups alone do not establish every mode. See [NAS-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#nas-1).
- **Local operation and data portability:** Preserve useful local capabilities and practicable exits for retained data while representing genuine remote dependencies honestly.
- **Product Platform Scope:** Declare Desktop, Mobile, Universal Device Application, and/or Web scope. First-class tested Desktop Linux baselines are Arch Linux, CachyOS, Ubuntu LTS, and Linux Mint (current stable Ubuntu-based release), with equal applicable support and validation expectations. Ubuntu or Mint testing does not establish support for other distributions; other mainstream distributions remain best-effort unless explicitly promoted. Browser support is distinct from native support. See [PORT-3](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#port-3).
- **One shared Rust core:** Product clients share domain and durable behavior where technically practical. Platform-appropriate UIs are preferred when resources allow; shared cross-platform UI is also a first-class option. Adapt presentation to desktop, phone, and tablet. See [CORE-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#core-1) and [UI strategy](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#ui-1).
- **Device continuity:** Preserve ordinary local operation without a permanent server. Applicable products support local-first device synchronization, an opt-in NAS hub, and safe topology transitions. See [synchronization](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s20).
- **Visual assets:** Prefer genuine SVG source artwork for naturally vector assets; retain raster content where appropriate, permit generated platform icons, respect official brand assets, and enforce SVG trust boundaries. See [ASSET-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#asset-1).
- **Information architecture and Hermes:** The **Hermes / User-Adaptable File Structure Blueprint** is now **integrated as candidate policy**, no longer pending design. It defines discoverability, stable identity independent of paths, relationships, source lineage, precise anchors, evidence status, and bounded AI retrieval through the core. Storage and user-facing organization remain domain-appropriate. Hermes stays optional and bounded; local/cloud clients receive no authority bypass. See [information architecture](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s32) and [Hermes retrieval](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#hermes-2).
- **Lifetime data and operation evidence:** Retained information is separated from disposable implementation state. Interfaces share logical application truth; portable exits preserve declared meaning. Applicable operations have recovery correlation/receipts and truthful unknown outcomes. Derived views are not accidental write authorities. See [LIFE-2](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#life-2), [CORE-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#core-1), and [OPS-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#ops-1).
- **Development governance:** Refine the idea, research alternatives, use the strongest reasonably available planning model, and pass the application Plan Freeze Gate before implementation. Keep discoverable APP Plan and Codebase responsibilities, a current Master Plan and Project State, executable phase specifications, and evidence-bearing Done Phases. See [section 31](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s31).
- **Full-build continuity and conformance:** A sufficiently capable small local model should be able to build the entire app from durable repository artifacts without hidden chat history or continuous stronger-model rescue. Missing information blocks affected execution; it does not authorize guessing. Every phase must pass Universal Rules, Master Plan, and Phase Contract checks. Brownfield applications undergo assessment and conformance repair before new features, preserving compliant work.
- **Lifecycle readiness:** Preserve proportionate release reconstruction instructions and critical-dependency dispositions; provide recovery without successful normal startup; plan and validate material lifetime growth. User-facing workflows include accessibility, and durable/interchange meaning is separated from display locale. See [SEC-5](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#sec-5), [RECOVER-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#recover-1), [DEV-16](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#dev-16), [UI-3](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#ui-3), and [DATA-4](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#data-4).
- **Explicit timezone policy in every App Plan:** Define actual timezone-sensitive behavior even without scheduling features. Keep instants, civil/recurring times, date-only values, durations, and monotonic intervals distinct; device travel must not silently reinterpret persisted meaning. Offsets and timezone-rule identities differ. See [DATA-5](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#data-5).
- **Malware and data protection:** Apply risk-based hostile-input handling, parser isolation, least privilege, compromise containment, suspicious-sync policy, protected recovery copies, restore validation, and update authorization/integrity. NAS sync alone is not independent backup, and encryption is not malware immunity. See [SEC-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#sec-1), [SEC-3](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#sec-3), [SYNC-1](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#sync-1), and [backup contracts](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s22). Effort follows retained-data value, attack surface, and architecture.

- **Raw intake and local malware scanning:** File-ingesting applications should prefer an explicit logical Raw/Intake boundary and a replaceable local scanner capability, evaluating ClamAV where suitable. Required checks gate promotion; startup evaluates every Raw object's verdict validity in the background without requiring a full historical byte rescan. New/changed files are queued promptly; failure is not clean. Scan status, signature freshness, quarantine, and receiving-device trust are explicit. See [IO-2](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#io-2), [IO-3](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#io-3), and [SEC-6](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#sec-6). No mandatory physical folder, scanner for irrelevant apps, cloud upload, or Linux-only mechanism is introduced.

- **UI/product governance:** Substantial products explain actual user value, then establish flows/information hierarchy, a design brief and system before substantial UI construction. Holistic anti-slop review, subtraction, deliberate density/color/type/motion, real states/content, accessible platform adaptation, rendered QA, and proportionate usability validation govern completion. 60/30/10 is a heuristic, and no font, color, card, gradient, or other primitive is universally banned. See [UI-4–UI-7](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#ui-4) and [DEV-18](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#dev-18).
- **Universal Agent Skills:** A normative catalog defines 33 reusable workflow families, portable inspectable guidance, progressive loading, trusted revisions, conflict/context management, and third-party review. Skills remain beneath owner/project/phase/design contracts and cannot grant execution authority or replace specifications. These are library responsibilities, not installed trusted packages. See [section 33](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#s33).

## Application development lifecycle

For new applications: refine the idea → research → write the Master Plan and phase contracts → review the candidate plan through Attack/Fix cycles → pass the Plan Freeze Gate → implement bounded phases → verify all three conformance layers → preserve Done Phases evidence and update Project State. Known material questions must be resolved or explicitly accepted and documented with applicable authority before implementation.

For existing applications when these rules are applied: pause ordinary feature work → inspect the authorized application → create/update the Master Plan and Existing App Assessment → preserve reusable work and define Conformance Phases → repair and verify → resume planned features subject to the same phase gate. Missing future roadmap features are distinct from defects in the inherited implemented scope.

Necessary emergency containment/repair may precede complete normal planning under [DEV-17](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#dev-17), within actual authority and with proportionate evidence. After material emergency changes, reconcile project records and pass the applicable Three-Layer Conformance Gate before ordinary features resume. Urgency does not manufacture permission or count as verified completion.

APP Plan is the durable specification and development memory; Codebase contains implementation. Exact folder names may vary. Project State is the concise machine-readable and human-readable execution entry point, not a second Master Plan. Evidence supports research and verification through artifacts or references; task execution records feed Done Phases without unnecessary duplication. Research preserves verified, inferred/conditional, and unknown claim status. Strongest-model planning implies no permanent cloud dependency. Verification checks actual artifacts against specifications; an agent's completion claim is insufficient.

These application workflows do not authorize inspecting another repository or conducting this constitution's final attack. APP Plan governs development; the runtime information blueprint governs the product's retained information. Small-model product use and small-model product development are distinct goals; neither substitutes for the other.

## Decisions and exceptions

The owner/user is the ultimate authority unless explicitly delegated. Formal policy exceptions record the rule, scope, technical reason, risks, mitigations, duration or review trigger, and approving authority with evidence. Expiry or material changes to assumptions, rationale, or scope trigger reconsideration; exceptions may be renewed, replaced, superseded, or withdrawn without arbitrary periodic bureaucracy. Ordinary default alternatives need a proportionate rationale; recommendations need no exception. Read [GOV-3](UNIVERSL%20RULES%20FOR%20ALL%20APPS.md#gov-3) before treating a difference as a policy violation.

ADRs in [decisions/](decisions/) preserve significant decisions and rationale. The constitution remains primary; supporting documents cannot silently add stronger rules.

## Review and change process

1. Identify the current base commit, affected rules, and applicable user decisions.
2. Make proposed changes on a reviewable branch and preserve historical evidence.
3. Record findings and their disposition, validate links and normative consistency, and distinguish documentation validation from runtime evidence.
4. Policy design is now owner-frozen. Ordinary brainstorming is closed; changes require the recorded defect-correction basis or explicit owner authorization to reopen design. Existing policy decisions are the review target.
5. Conduct Red only in a fresh task against the identified frozen candidate under GOV-5. Authorized Green Fix records findings, corrections, validation and the new revision, invalidating earlier clean Red passes. Convergence and ratification remain separate; no authority to inspect other repositories, push, merge or release is implied.

Rule anchors are preferred over old section numbers. Historical review section references refer to the recorded original commit, not this renumbered candidate.
