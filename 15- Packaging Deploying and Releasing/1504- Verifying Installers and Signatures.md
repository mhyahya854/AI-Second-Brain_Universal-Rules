### 25.6. SEC-6 — Replaceable native malware-scanning capability

**Type:** ECOSYSTEM POLICY | **Origin:** USER POLICY | **Applies:** applications/security components benefiting from file malware detection

Projects SHOULD evaluate and prefer ClamAV as the default open-source malware engine where platform support, licensing, distribution, performance, and threat-model benefit are suitable. ClamAV is replaceable, not canonical architectural authority. Product code MUST depend on a generic malware-scanning capability boundary; engine-specific details belong in the adapter, not core product semantics. A suitable alternative or supplementary engine MAY be deliberately selected with documented rationale without requiring an exception merely for replacing this preferred implementation. Selection, platform adapters, and any explicitly designed multi-engine pipeline MUST comply with [NOFALL-1](../0-%20Start%20Here%20and%20Universal%20Rules/002-%20The%20Universal%20Constitution.md#nofall-1)–[NOFALL-2](../0-%20Start%20Here%20and%20Universal%20Rules/002-%20The%20Universal%20Constitution.md#nofall-2): engine failure MUST NOT trigger substitute execution or turn an unmet scan gate into success. A future engine replacement follows deliberate planning, migration, and verification; it is not a hidden runtime fallback. Typed operations such as `scan_object`, `scan_stream`, `query_scan_status`, and `quarantine`, or equivalent contracts, preserve core-controlled authorization, outcomes, and promotion.

Scanning SHOULD execute locally on the user's device or authorized local infrastructure. Ordinary scanning MUST NOT require uploading private files to a cloud scanner; cloud scanning may only be an explicitly authorized optional capability under [PRIV-2](../6-%20Writing%20the%20Complete%20Master%20Plan/606-%20Documenting%20Data%20Security%20and%20Recovery.md#priv-2). Where practical, prefer a constrained scanner process/service behind protected local IPC for crash isolation, resource limits, bounded filesystem/network access, privilege separation, replaceability, and security updates. Direct library integration remains permissible with technical and licensing justification; neither integration mechanism is universal. [SEC-1](../7-%20Attacking%20and%20Freezing%20the%20Master%20Plan/703-%20Finding%20Security%20and%20Privacy%20Risks.md#sec-1) and [AUTH-1](../10-%20Building%20the%20Core%20and%20Backend/1007-%20Implementing%20Security%20and%20Authorization.md#auth-1) still govern effective boundaries.

For `clamd` or equivalent daemons, the scanner interface MUST remain local/protected unless an explicitly secured architecture justifies another deployment. Unauthenticated TCP listeners MUST NOT be exposed to the public Internet or untrusted networks. Prefer protected local sockets/IPC, constrained loopback, or equivalent platform transport; locality alone does not supply authorization. Preserve declared Windows, macOS, Linux, and other product targets under [PORT-3](../3-%20Deciding%20the%20Stack/302-%20Choosing%20Supported%20Platforms.md#port-3); Linux-only ClamAV on-access functionality MUST NOT become a universal dependency. Platform-specific adapters may differ behind the capability contract. Scanning/signature failure follows [IO-3](../10-%20Building%20the%20Core%20and%20Backend/1008-%20Implementing%20Required%20Core%20Capabilities.md#io-3) without giving the scanner canonical mutation authority.

When a ClamAV source archive is incorporated into an application or shared security component, record its version, upstream source/repository, exact revision if available, archive/source digest, license/notices, acquisition/import date, local modifications, build configuration, and update strategy under [SEC-4](../2-%20Researching%20Existing%20Projects%20and%20Filling%20the%20Gaps/209-%20Choosing%20What%20to%20Reuse%20or%20Build.md#sec-4) and [SEC-5](1502-%20Preparing%20Reproducible%20Production%20Builds.md#sec-5). Preserve modification history; do not silently alter vendored security source. Before distribution, verify the actual integration and redistribution model against applicable GPLv2 obligations and relevant bundled-component licenses. This policy does not establish that a particular archive, linking/process arrangement, or distribution is compliant. Importing a foreign-language engine remains governed by [LANG-1](../3-%20Deciding%20the%20Stack/303-%20Choosing%20Programming%20Languages.md#lang-1)'s dependency/artifact scope; it does not justify independently rewriting the shared Rust product core.
